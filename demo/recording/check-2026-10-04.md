# A check on the new server, 2026-10-04

ConfigHub's hosted server moved from v0.8.1 to v0.8.3 on 4 October, after the
two recorded runs. This check re-ran, from the docs as they stand, the parts a
server change could break. Milton approved onboarding; everything else was run
by hand, under the agents' identities where the docs name one.

Versions: ConfigHub server v0.8.3, `cub` v0.8.1, `cub sveltos` v0.13.0,
Sveltos v1.15.0, kind v0.31.0. A fresh `AI_CHAOS_DIR`, so no earlier run
was in play. All times UTC.

| Part | What ran | Result |
| --- | --- | --- |
| Stand-up | `bash demo/standup.sh` | Six kind clusters, the shop and Reloader, and the four identities (Devil, Angel, Milton and the reporter) signed in, in about eight minutes |
| Onboarding | `scenarios/00-onboard.md` as written, with Milton approving | Milton approved staging and prod for both components, each on its first review (09:40 to 09:50). The handover delivered every profile from ConfigHub, with nothing reinstalled. All nine Spaces Synced and Healthy |
| Gates and live status | `setup/gates.sh`, `setup/reporter.sh start` | Rollouts required; the record gated; live status written every 15 s |
| The parity check passes | `cub sveltos check --change-order chaos-shop-base/onboard-d244df9f --stage prod --parity-with staging`, as Angel | "passed shop/2; recorded a Pass" in all three prod Spaces |
| The parity gate | `scenarios/03-parity.md` step 10, as the person running the demo | Prod's release needs an approval and Angel's ParityCheck |
| A prod-only change is refused | As Devil: api's memory limit 128Mi to 96Mi in `chaos-shop-class-prod` only, a change order promoted to prod, then `cub release publish chaos-shop-prod-eu` | Refused, as below |
| The parity check fails | `cub sveltos check ... --parity-with staging`, as Angel | Failed in all three prod Spaces, naming the field, as below |
| The withdrawal | As Devil: the order aborted, the units restored | All four units back at 128Mi |
