units of each space its start tag marks. A unit it covered but carried no changes for is marked

revisions after it, if any, are somebody else's change.

Undoing a change order in a unit happens once, as promoting it into one does: a unit already

units it did not, and a unit edited forward since it was undone keeps that work.

# Approval request for the approver: guardrails on every cluster

**Change order:** `chaos-platform-base/guardrails-secret-env-reload-r3`, waiting at staging on workflow `chaos-platform-base/rollout`. Nothing is released: no cluster has a policy yet.

## What broke, and the cause
In outage 1, `shop/web` read `SHOP_TOKEN` from the Secret `shop-token` once, at start. The token was rotated and nothing restarted `web`, so it kept the old token and went unready. Nothing in the fleet stopped a Deployment like that from being admitted.

## The change
A new unit `guardrails` in `chaos-platform-base`, with nothing else touched:

```diff
+ kind: ValidatingAdmissionPolicy        # secret-env-needs-reload
+   failurePolicy: Fail
+   matchConstraints: apps/v1 deployments, CREATE and UPDATE
+   validation: reloader.stakater.com/auto == "true"
+               OR every Secret taken by env secretKeyRef / envFrom secretRef
+                  (containers and initContainers) is named in
+                  secret.reloader.stakater.com/reload
+ kind: ValidatingAdmissionPolicyBinding  # secret-env-needs-reload
+   validationActions: [Deny]
```

- **Exemptions:** none. No namespace, user or workload is excluded.
- **Not covered:** Secrets mounted as files are not covered by the rule, because the kubelet refreshes them.
- **Known cases:** the new Space `chaos-policies` (no target, delivered nowhere) holds the unit `known-cases` with 11 example Deployments.

## What checked it
The three previews ran against `guardrails@3`, the revision in the change order, with no policies in force.

| Preview | Newly denied | Unchanged | What was refused |
|---|---|---|---|
| `--component chaos-shop` (what runs now, `shop@2`) | 4 | 4 | `Deployment web` on staging, prod-eu, prod-us-1 and prod-us-2; `api` stays allowed |
| `--component chaos-shop --next` (my fix, `shop@3`) | 0 | 8 | nothing |
| `--component chaos-platform` (`reloader@2`) | 0 | 4 | nothing |

- **Known cases:** all 11 behave as expected under the candidate.
  - **Denied (6):** `web` before the fix (staging and prod), `envFrom` with no annotation, an annotation naming the wrong Secret, `auto: "false"`, and two Secrets with only one named.
  - **Allowed (5):** `web` with the fix (staging and prod), `envFrom` with `auto`, a Secret mounted as a file, and two Secrets both named.
- **Policy unchanged after preview:** the only thing it refuses in the fleet is `web` as it runs today, which is the broken configuration, so I did not loosen it.
- **Unmanaged Deployments:** coredns, local-path-provisioner and sveltos-agent-manager take no Secret through their environment on any of the four clusters (checked with kubectl).

## Release order
Release the fix first, then the guardrails, in each stage:

1. Staging: `chaos-shop-base/web-reload-on-token-rotation`, then this order.
2. Prod: the same order again.

The first preview shows why: `web` as it runs today is refused by the policy on all four clusters. A ValidatingAdmissionPolicy does not evict what runs, but with the guardrails in first, any update to the unfixed `web` would be denied. I expect that to include Sveltos re-applying the current shop configuration, which would then report the shop as failing; I have not tested that. The fix itself would still be admitted, so the wrong order would not deadlock.

## What could go wrong
- **Runtime errors block Deployment writes.** With `failurePolicy: Fail`, an expression that errors at admission would refuse every Deployment create or update on that cluster, system ones included. The sandbox evaluated the policy without error on every object above.
- **Future workloads can be refused.** Any Deployment, in any namespace, that later takes a Secret through its environment without one of the two annotations will be denied. That is the intent, but it also applies to third-party charts.
- **Other Reloader forms are not accepted.** Only the two annotations you named pass; `secret.reloader.stakater.com/auto` or the search/match form would be refused.
- **Only Deployments are covered.** StatefulSets and DaemonSets are outside the rule as given.
- **The annotation is not proof of a restart.** The policy checks that the annotation is there, not that Reloader is running.
